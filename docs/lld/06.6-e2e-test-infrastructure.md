# LLD 6.6: E2E Test Infrastructure (Playwright)

End-to-end test harness using Playwright that exercises the full stack — frontend, backend, and Supabase — through a headless browser. This LLD defines the infrastructure, fixtures, and CI pipeline. It does NOT define individual test scenarios (those are added by future LLDs as features are built).

---

## 1. Scope

### In scope

- Playwright configuration file (`playwright.config.ts`) with projects for Chromium (headless)
- Directory structure for E2E tests (`e2e/`)
- Playwright `webServer` config to auto-start the backend and Vite dev server before tests run (both locally and in CI)
- Vite proxy configuration so the frontend can reach the backend without nginx
- CI job (`e2e-tests`) in GitHub Actions that boots Supabase, builds the app, starts services directly (no Docker), and runs Playwright
- App readiness mechanism — health check polling before Playwright connects
- Test data strategy: Supabase admin SDK for user creation, guest session helpers, database reset between test files
- Auth fixtures: create users via admin API, obtain tokens programmatically, inject into `storageState` directly (no UI login in setup)
- Page object / helper pattern for common interactions (create game, join as guest)
- `data-testid` attribute additions to existing frontend components (enumerated below)
- npm scripts: `test:e2e`, `test:e2e:ui` (headed mode for debugging)

### Out of scope

- Individual test scenarios (login flow, game play flow, game over) — added by future LLDs
- Visual regression / screenshot comparison testing
- Mobile viewport testing (Phase 5 polish)
- Performance testing
- Cross-browser testing (Firefox, WebKit) — Chromium only for now
- Docker Compose for E2E (not used — services run directly on the host)
- The existing integration tests (LLD 6.5) — they remain separate, testing backend APIs without a browser

## 2. Approach

### Key decisions

1. **Playwright over Cypress.**

   Playwright is lighter, runs headless Chromium natively on Linux (confirmed working on this Cloud Desktop and GitHub Actions ubuntu-latest), supports multiple browser contexts per test for multiplayer scenarios, and has first-class `webServer` support for auto-starting the app.

   *Rationale:* Multiplayer card games require multiple independent browser sessions in a single test (4 players). Playwright's `browser.newContext()` makes this trivial. Cypress requires separate process instances for multi-user tests.

2. **No Docker Compose — services run directly on the host (both local and CI).**

   Playwright's `webServer` option starts the backend directly (`node build/backend/index.js`) and the frontend via Vite dev server (`npx vite`). This is the same approach for both CI and local dev. No containers, no nginx, no image builds.

   *Rationale:* The project has no production deployment target yet, so "production parity" is not a concern. Running services directly avoids `.env` file mapping issues, "localhost inside container" networking problems, and slow Docker image rebuilds. This matches the pattern already established by the integration tests CI job which runs `node build/backend/index.js` after `npm run build:backend`.

3. **Vite proxy for API routing (replaces nginx).**

   Since there is no nginx reverse proxy, the Vite dev server is configured with `server.proxy` to forward `/api` and `/socket.io` requests to the backend on port 3000. The Playwright `baseURL` is `http://localhost:5173` (Vite dev server) for both local and CI.

   *Rationale:* Same URL scheme everywhere. Frontend code already uses relative paths (`/api/...`), so the proxy makes them hit the backend transparently.

4. **One Playwright project targeting Chromium only.**

   Single project `chromium` in headless mode. Cross-browser testing adds CI time without catching bugs relevant to game logic — the app is a simple SPA with standard browser APIs. Add Firefox/WebKit if CSS bugs are found later.

   *Rationale:* Deploy cheap principle. Chromium covers 70%+ of target users. Additional browsers can be added as a one-line config change.

5. **Auth via Supabase Admin SDK + `storageState` injection (no UI login in setup).**

   Global setup uses the Supabase admin client (`service_role` key) to create test users programmatically via `supabase.auth.admin.createUser()`. It then calls `supabase.auth.signInWithPassword()` to obtain session tokens, and writes them directly into Playwright `storageState` JSON files. No browser is opened during setup.

   *Rationale:* Decouples setup from the login page UI. If the login form changes, setup does not break. Faster (no browser spin-up for login). More reliable (no UI timing issues).

6. **Multiplayer tests use multiple `BrowserContext` instances.**

   A single test can create 4 browser contexts (one per player), each with its own storage state. This simulates 4 distinct players interacting with the same game simultaneously.

   *Rationale:* This is the core E2E scenario — 4 people playing a card game. Other approaches (4 separate test processes) are harder to coordinate and slower.

7. **Supabase started externally (not by Playwright).**

   Both locally and in CI, Supabase must already be running before E2E tests start. Playwright's `webServer` starts only the app (not Supabase). The E2E npm script documents this prerequisite.

   *Rationale:* Supabase startup is slow (~15s locally, ~60s CI cold start). Starting it per test run is wasteful. It should already be running (developers run `supabase start` once; CI starts it in a prior step).

### Auth fixture (global setup)

```typescript
// e2e/global-setup.ts

import { test as setup } from "@playwright/test";
import { createClient } from "@supabase/supabase-js";
import * as fs from "node:fs";
import * as path from "node:path";

const SUPABASE_URL = process.env.SUPABASE_URL || "http://localhost:54321";
const SUPABASE_SERVICE_ROLE_KEY =
  process.env.SUPABASE_SERVICE_ROLE_KEY || "";
const SUPABASE_ANON_KEY = process.env.SUPABASE_ANON_KEY || "";

// Test user credentials — created in Supabase during setup
const TEST_USERS = [
  { email: "e2e-player1@test.local", password: "testpass123", name: "Player1" },
  { email: "e2e-player2@test.local", password: "testpass123", name: "Player2" },
  { email: "e2e-player3@test.local", password: "testpass123", name: "Player3" },
  { email: "e2e-player4@test.local", password: "testpass123", name: "Player4" },
];

setup("create test users and save auth state", async () => {
  // Admin client for user creation (uses service_role key)
  const adminClient = createClient(SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY, {
    auth: { autoRefreshToken: false, persistSession: false },
  });

  // Anon client for sign-in (mimics what the app does)
  const anonClient = createClient(SUPABASE_URL, SUPABASE_ANON_KEY, {
    auth: { autoRefreshToken: false, persistSession: false },
  });

  // Ensure .auth directory exists
  const authDir = path.resolve(__dirname, ".auth");
  fs.mkdirSync(authDir, { recursive: true });

  for (let i = 0; i < TEST_USERS.length; i++) {
    const user = TEST_USERS[i]!;

    // Create user via admin API (idempotent — ignores "already registered" errors)
    await adminClient.auth.admin.createUser({
      email: user.email,
      password: user.password,
      email_confirm: true, // Skip email confirmation
      user_metadata: { display_name: user.name },
    });

    // Sign in to get session tokens
    const { data, error } = await anonClient.auth.signInWithPassword({
      email: user.email,
      password: user.password,
    });

    if (error || !data.session) {
      throw new Error(
        `Failed to sign in test user ${user.email}: ${error?.message}`,
      );
    }

    // Write storageState JSON that Playwright can load directly.
    // The frontend reads tokens from localStorage under the Supabase storage key.
    const storageKey = `sb-${new URL(SUPABASE_URL).hostname.split(".")[0]}-auth-token`;
    const storageState = {
      cookies: [],
      origins: [
        {
          origin: "http://localhost:5173",
          localStorage: [
            {
              name: storageKey,
              value: JSON.stringify({
                access_token: data.session.access_token,
                refresh_token: data.session.refresh_token,
                expires_at: data.session.expires_at,
                token_type: "bearer",
                user: data.session.user,
              }),
            },
          ],
        },
      ],
    };

    fs.writeFileSync(
      path.join(authDir, `player${i + 1}.json`),
      JSON.stringify(storageState, null, 2),
    );
  }
});
```

### Page helpers

```typescript
// e2e/helpers/game-helpers.ts

import { type Page, type BrowserContext, expect } from "@playwright/test";

/**
 * Creates a new game as the logged-in user and returns the game ID.
 */
export async function createGame(
  page: Page,
  options?: { maxPlayers?: number },
): Promise<string> {
  await page.goto("/");
  await page.click('[data-testid="create-game-link"]');
  // Select game type
  await page.selectOption('[data-testid="game-type-select"]', "big2");
  // Select player count if provided
  if (options?.maxPlayers) {
    await page.fill(
      '[data-testid="max-players-input"]',
      String(options.maxPlayers),
    );
  }
  await page.click('[data-testid="submit-create-game"]');
  // Wait for lobby to load — URL changes to /game/:id
  await page.waitForURL(/\/game\/.+/);
  const url = page.url();
  const gameId = url.split("/game/")[1]!;
  return gameId;
}

/**
 * Joins an existing game as a guest with the given display name.
 */
export async function joinAsGuest(
  page: Page,
  gameId: string,
  displayName: string,
): Promise<void> {
  await page.goto(`/game/${gameId}/join`);
  // Should see guest entry form
  await page.fill('[data-testid="guest-name-input"]', displayName);
  await page.click('[data-testid="guest-join-button"]');
  // Wait for lobby to appear
  await expect(page.locator('[data-testid="game-lobby"]')).toBeVisible();
}

/**
 * Joins an existing game as a registered (already logged-in) user.
 */
export async function joinAsRegistered(
  page: Page,
  gameId: string,
): Promise<void> {
  await page.goto(`/game/${gameId}`);
  // Registered user sees the lobby directly (auto-join)
  await expect(page.locator('[data-testid="game-lobby"]')).toBeVisible();
}

/**
 * Waits for the game board to appear (game has started).
 */
export async function waitForGameBoard(page: Page): Promise<void> {
  await expect(page.locator('[data-testid="game-board"]')).toBeVisible({
    timeout: 10_000,
  });
}
```

### Health check utility

```typescript
// e2e/helpers/wait-for-app.ts

/**
 * Polls the backend health endpoint until it responds 200.
 * Used as a safety check if webServer startup is slow.
 */
export async function waitForApp(
  baseUrl: string,
  timeoutMs = 60_000,
): Promise<void> {
  const start = Date.now();
  while (Date.now() - start < timeoutMs) {
    try {
      const res = await fetch(`${baseUrl}/echo`);
      if (res.ok) return;
    } catch {
      // Not ready yet
    }
    await new Promise((r) => setTimeout(r, 1000));
  }
  throw new Error(`App at ${baseUrl} did not become ready within ${timeoutMs}ms`);
}
```

## 6. State Model

### Test data lifecycle

1. **Global setup (once per test run):** Creates 4 test users in Supabase via the admin SDK (`service_role` key). Signs them in programmatically and writes their session tokens into `e2e/.auth/playerN.json` storage state files. No browser is opened.

2. **Per test file:** Each test creates its own game. No shared game state between test files. Games are created fresh, played (or partially played), and abandoned. The database accumulates test games but this does not affect isolation because each test operates on its own game ID.

3. **Database cleanup:** Not performed between tests. Supabase local instance is ephemeral (destroyed by `supabase stop`). For CI, the Supabase instance is fresh per workflow run. For local dev, developers can run `supabase db reset` if they want a clean slate. No `TRUNCATE` logic in test code.

### App startup sequence (CI and local — same approach)

```
1. supabase start                  -- Starts Postgres, GoTrue, PostgREST, etc.
2. Export env vars                 -- SUPABASE_URL, ANON_KEY, SERVICE_ROLE_KEY, JWT_SECRET, DB_*
3. npm ci                          -- Install deps
4. npm run build                   -- Build frontend + backend (single build step)
5. npx playwright test             -- webServer starts backend (node build/backend/index.js)
                                   -- webServer starts Vite dev server (npx vite --port 5173)
                                   -- Vite proxy routes /api and /socket.io to backend:3000
                                   -- Tests run against http://localhost:5173
6. Upload artifacts on failure     -- HTML report + traces (CI only)
```

## 7. Edge Cases

1. **Supabase not running.** Global setup fails at user creation with a connection error. The error message is: "Cannot reach Supabase at localhost:54321. Run `supabase start` first." Tests abort before any browser launches.

2. **Backend not ready when Vite starts.** The `webServer` config lists the backend first with its health check URL (`http://localhost:3000/echo`). Playwright waits for it to respond before proceeding. The Vite dev server starts second and is also health-checked.

3. **Port conflict.** If port 3000 or 5173 is already in use, `reuseExistingServer: true` means Playwright will use the existing process. This is intentional for local dev iteration (leave services running between test runs).

4. **Stale auth state files.** If Supabase is reset (users deleted), the `e2e/.auth/` files contain expired tokens. The global setup re-creates users and re-saves state on every run. The `.auth/` dir is gitignored and treated as ephemeral.

5. **Test isolation with serial execution.** Tests run serially (`workers: 1`) to avoid race conditions on shared Supabase state (game creation, user sessions). Each test creates a fresh game, so ordering does not matter — but parallelism could cause port/resource conflicts.

6. **Frontend build requires env vars.** The Vite build needs `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` at build time (baked into the frontend bundle). The CI workflow must export these before `npm run build`. Locally, `.env` provides them.

7. **Trace/video artifacts can be large.** Configured to capture only on first retry (not every run). CI uploads artifacts only when the job fails.

8. **Service role key availability.** The Supabase local dev setup always provides a service role key via `supabase status`. CI extracts it the same way. The key is only used in test setup, never exposed to the frontend.

## 8. CI Job Design

Add to `.github/workflows/ci.yml`:

```yaml
  e2e-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - uses: supabase/setup-cli@v1
        with:
          version: latest
      - run: supabase start
      - name: Export Supabase env vars
        run: |
          echo "SUPABASE_URL=http://localhost:54321" >> $GITHUB_ENV
          echo "SUPABASE_ANON_KEY=$(supabase status -o env | grep ANON_KEY | cut -d= -f2)" >> $GITHUB_ENV
          echo "SUPABASE_SERVICE_ROLE_KEY=$(supabase status -o env | grep SERVICE_ROLE_KEY | cut -d= -f2)" >> $GITHUB_ENV
          echo "SUPABASE_JWT_SECRET=$(supabase status -o env | grep JWT_SECRET | cut -d= -f2)" >> $GITHUB_ENV
          echo "VITE_SUPABASE_URL=http://localhost:54321" >> $GITHUB_ENV
          echo "VITE_SUPABASE_ANON_KEY=$(supabase status -o env | grep ANON_KEY | cut -d= -f2)" >> $GITHUB_ENV
          echo "DB_HOST=localhost" >> $GITHUB_ENV
          echo "DB_PORT=54322" >> $GITHUB_ENV
          echo "DB_USER=postgres" >> $GITHUB_ENV
          echo "DB_PASSWORD=postgres" >> $GITHUB_ENV
          echo "DB_NAME=postgres" >> $GITHUB_ENV
      - run: npm ci
      - run: npx playwright install chromium --with-deps
      - run: npm run build
      - name: Run E2E tests
        run: npx playwright test
      - name: Upload Playwright report
        if: failure()
        uses: actions/upload-artifact@v4
        with:
          name: playwright-report
          path: playwright-report/
          retention-days: 7
      - name: Upload test traces
        if: failure()
        uses: actions/upload-artifact@v4
        with:
          name: playwright-traces
          path: test-results/
          retention-days: 7
```

This job runs in parallel with `unit-tests` and `integration-tests`. Note: no Docker Compose build, no Docker image step. The `webServer` config in `playwright.config.ts` handles starting the backend and Vite directly.

## 12. Test Requirements

### Infrastructure validation (this LLD's deliverables)

- **Smoke test (1 test):** Authenticated user sees home page with "Create Game" link visible (proves auth fixture + storageState injection + Vite proxy + page rendering all work)
- **Guest entry test (1 test):** Unauthenticated visit to game join URL shows the guest entry component with "Join as Guest" heading (proves routing + component rendering without auth)

### What this LLD enables (future LLDs add)

Future feature LLDs will add E2E specs under `e2e/` for:
- Full login/signup flow (submit form, verify redirect)
- Game creation and lobby (create, share link, see players join)
- Full 4-player game flow (create, join, start, play to completion)
- Guest flow (arrive via link, enter name, play)
- Game over and rematch

### Convention for adding E2E tests

When implementing a feature LLD that has user-facing UI changes:
1. Add a `.spec.ts` file under `e2e/` named after the feature (e.g., `e2e/game-flow.spec.ts`)
2. Import helpers from `e2e/helpers/`
3. Use `browser.newContext({ storageState })` for authenticated sessions
4. Use multiple contexts for multiplayer scenarios
5. Add any new page helpers to `e2e/helpers/game-helpers.ts`
6. Ensure relevant DOM elements have `data-testid` attributes

### What NOT to test via E2E

- Game engine logic (361 unit tests cover this)
- Backend API correctness (13 integration tests cover this)
- Component rendering details (visual tests are out of scope)
- Performance (E2E tests are for correctness, not speed)

### Iterating on tests

Use `test:e2e:ui` for the fastest feedback loop. Playwright UI mode shows the browser, allows step-through, and auto-reruns on file save. The `webServer` config with `reuseExistingServer: true` means you can leave the backend running between test runs.

For frontend changes, the Vite dev server provides HMR — no rebuild needed between runs.
