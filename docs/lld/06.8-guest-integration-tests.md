# LLD 6.8: Guest Flow Integration & E2E Tests

Integration tests covering the guest user lifecycle at the API/WebSocket level, plus E2E Playwright tests for the guest browser flow. This catches the class of bugs where guest tokens are not properly attached/verified across layers (e.g., the recently fixed axios interceptor issue causing 401s on getGameState).

---

## 1. Scope

### In scope

- Integration tests for the complete guest lifecycle via REST API
- Integration tests for guest WebSocket connectivity and gameplay
- Integration tests for the guest-to-registered claim flow
- Tests for edge cases: expired tokens, invalid tokens, wrong gameId, duplicate sessions
- Multi-guest game scenario (4 guests playing a full game)
- E2E Playwright tests for the guest browser flow (join via invite link, enter name, reach lobby, play)

### Out of scope

- Unit tests for `guestToken.ts` or `guestSessionStore.ts` (already testable as pure functions)
- Changes to production code (this is test-only)
- Performance testing (many concurrent guest sessions)

---

## 2. Approach

### Key decisions

1. **Single new test file: `tests/integration/guest-flow.test.ts`.**

   All guest-specific tests live in one file. The existing test files already have minimal guest coverage (auth.test.ts has 2 guest tests, websocket-game.test.ts has 1 guest test). This new file provides comprehensive coverage without duplicating the existing tests.

   *Rationale:* The existing tests prove basic guest auth works. This file tests the full lifecycle including session creation, rejoining, claiming, expiry, and multi-guest play. Keeping them in one file follows the convention established by LLD 6.5 (one feature = one test file).

2. **Reuse existing helpers (`createTestGuest`, `createTestUser`, `createAuthenticatedSocket`).**

   No new helpers needed. The existing `guestUser.ts` helper creates guest sessions. The existing `socketClient.ts` helper connects with any token (guest or registered).

3. **Self-contained tests with per-describe server lifecycle.**

   One `createTestServer()` call in `beforeAll`. Each test creates its own game and guests. No shared state between tests.

4. **Game completion strategy reused from `websocket-game.test.ts`.**

   The multi-guest full game test uses the same `pickCardsToPlay` strategy from the existing WebSocket test file. Extract it into a shared helper within the test file (not a new helper module) to keep things simple.

5. **Token expiry tested via direct store manipulation, not by waiting.**

   The `GuestSessionStore` is in-memory and accessible through the test server. However, since we don't expose it, we instead craft an expired token by creating a session, then advancing the clock with `vi.useFakeTimers` / `vi.advanceTimersByTime`. Alternative: create a guest token manually with an already-expired timestamp (simpler, no timer manipulation needed). We use the manual approach since `createGuestToken` accepts an arbitrary `expiresAt`.

   *Rationale:* Waiting 4 hours for real expiry is obviously not viable. Manually crafting an expired token tests the same code path (the `verifyGuestToken` function checks `Date.now() > expiresAt`).

## 4. Test Specifications

### describe("Guest session creation")

```
it("POST /guest/session creates a valid guest session")
  - Registered user creates a game
  - POST /guest/session { displayName: "Alice", gameId }
  - Assert 200 response
  - Assert response has { guestId: string, displayName: "Alice", token: starts with "guest:", gameId }

it("rejects guest session for non-existent game")
  - POST /guest/session { displayName: "Alice", gameId: "non-existent-uuid" }
  - Assert 404 response

it("rejects guest session with empty displayName")
  - Registered user creates a game
  - POST /guest/session { displayName: "", gameId }
  - Assert 400 response

it("rejects guest session with displayName exceeding max length")
  - Registered user creates a game
  - POST /guest/session { displayName: "A".repeat(21), gameId }
  - Assert 400 response

it("deduplicates display names when multiple guests use the same name")
  - Registered user creates a game
  - Create guest 1 with displayName "Player"
  - Create guest 2 with displayName "Player"
  - Assert guest 1 displayName is "Player"
  - Assert guest 2 displayName is "Player2"
```

### describe("Guest joining a game")

```
it("guest token is accepted by joinGame endpoint")
  - Registered user creates a game
  - Create guest session for that game
  - POST /joinGame with guest token
  - Assert 200, body.gameId matches

it("guest appears in game state after joining")
  - Registered user creates a game
  - Create guest, join game
  - GET /getGameState with guest token
  - Assert response contains guest's ID in playerIds
  - Assert playerDisplayNames contains the guest's display name

it("rejects guest joining with token for a different game")
  - Registered user creates game A and game B
  - Create guest session for game A
  - POST /joinGame with guest token, body: { gameId: gameBId }
  - Assert 200 (the join handler validates gameId from body, not token)
  - NOTE: The token's gameId is NOT checked by joinGame — auth only checks session exists.
    The guest can technically join any game they have a valid session for. This tests current behavior.

it("guest cannot create a game (403)")
  - Registered user creates a game, create guest session
  - POST /createGame with guest token
  - Assert 403 (AccessDenied)
```

### describe("Guest accessing game state")

```
it("guest can GET /getGameState with their token")
  - Registered user creates a game
  - Guest creates session and joins
  - GET /getGameState?gameId=... with guest token
  - Assert 200
  - Assert gameState.playerIds includes guest's ID
  - Assert gameState.status is "CREATED"

it("guest receives filtered player view (no other hands visible)")
  - Create a 4-player game (1 registered + 3 guests), start it
  - Each guest GET /getGameState
  - Assert each response contains only that guest's hand (via engine view filtering)
  - NOTE: getGameState returns raw game state at the DB level (not engine view). 
    This test verifies the playerIds/status are correct. Information hiding is tested
    via WebSocket (game:state event uses engine.getPlayerView).
```

### describe("Guest WebSocket connection")

```
it("guest connects via WebSocket with guest token")
  - Registered user creates a game, guest creates session and joins
  - createAuthenticatedSocket(baseUrl, guest.token)
  - Assert socket.connected === true

it("guest receives game:state after game:join + game:start")
  - Create 4-player game (1 registered + 3 guests)
  - All 4 connect via WebSocket
  - All 4 emit game:join
  - Host emits game:start
  - Assert all guests receive game:state with hand.length > 0

it("rejects WebSocket connection with expired guest token")
  - Registered user creates a game
  - Manually craft a guest token with expiresAt = Date.now() - 1000
  - Attempt createAuthenticatedSocket with the expired token
  - Assert connection fails with error containing "UNAUTHORIZED"

it("rejects WebSocket connection with tampered guest token")
  - Take a valid guest token and flip one character in the HMAC portion
  - Attempt WebSocket connection
  - Assert connection fails with error containing "UNAUTHORIZED"
```

### describe("Guest playing in-game")

```
it("guest can emit game:action and play cards")
  - Create 4-player game with 1 registered + 3 guests
  - Connect all via WebSocket, join rooms, start game
  - Wait for game:state
  - Find which player's turn it is
  - If it's a guest's turn, emit game:action with a valid play
  - Assert ack.success === true
  - Assert all players receive updated game:state

it("server overrides playerId in guest action (anti-spoofing)")
  - Create 4-player game, start it
  - Guest emits game:action with { playerId: "spoofed-id", ... }
  - Assert the action is processed with the guest's real ID (not the spoofed one)
  - (This is implicitly tested by action success — the handler uses socket.data.userId)
```

### describe("Guest session expiry and edge cases")

```
it("request with no Authorization header returns 401")
  - POST /joinGame with no Authorization header
  - Assert 401

it("request with malformed guest token returns 401")
  - POST /joinGame with Authorization: "Bearer guest:not-valid-base64!"
  - Assert 401

it("request with well-formed but non-existent session returns 401")
  - Create a real guest token with valid HMAC but a guestId not in the session store
  - (Achievable by creating a session, then creating a new server instance — but simpler
    to just use a fabricated token with wrong HMAC that passes format check but fails HMAC)
  - Assert 401
```

### describe("Guest-to-registered claiming")

```
it("POST /guest/claim links guest game to new account")
  - Registered user A creates a game
  - Guest joins the game
  - New user B registers (createTestUser)
  - User B POST /guest/claim with { guestToken: guest.token }, authenticated as user B
  - Assert response: { success: true, gamesLinked: 1 }
  - GET /getGameState as user B
  - Assert user B's ID is now in playerIds (replacing guest's ID)

it("claim with expired guest token returns gamesLinked: 0")
  - Manually craft a token with expiresAt in the past
  - Registered user POST /guest/claim with the expired token
  - Assert response: { success: true, gamesLinked: 0 }

it("claim with guest not in any game returns gamesLinked: 0")
  - Create a guest session but do NOT join the game
  - New user POST /guest/claim with the guest token
  - Assert response: { success: true, gamesLinked: 0 }

it("guest cannot call /guest/claim (403)")
  - Create a guest session
  - POST /guest/claim with the guest token as auth (not in body)
  - Assert 403 (registeredOnlyMiddleware rejects guests)
```

### describe("Multiple guests in one game")

```
it("4 guests can join and play a complete Big2 game")
  - Registered user creates a game
  - Create 3 guest sessions, all join game
  - Registered user + 3 guests = 4 players
  - All connect via WebSocket
  - All emit game:join
  - Host emits game:start
  - Play game to completion using pickCardsToPlay strategy
  - Assert game status === "COMPLETED"
  - Assert all players have finishing positions

it("4 guests (no registered user) cannot start a game alone")
  - Actually: a game requires a registered user to CREATE it, but guests can be all remaining players.
  - A fully-guest game is not possible because POST /createGame requires registered auth.
  - This test documents that constraint (no assertion needed — it's tested by "guest cannot create a game")
```

### describe("Guest rejoining")

```
it("guest with existing session can rejoin without duplicate")
  - Registered user creates a game
  - Guest creates session and joins game
  - Guest calls POST /joinGame again with same token
  - Assert 200 (idempotent — joinGame returns success for already-joined player)
  - GET /getGameState — assert guest appears exactly once in playerIds

it("guest can re-create session with existingGuestId after disconnect")
  - Registered user creates a game
  - Guest creates session and joins game
  - Guest creates NEW session with existingGuestId = original guestId
  - Assert new session has same guestId as original
  - POST /joinGame with new token
  - Assert success, guest still in game with same ID
```

## 5. Helper: Expired Token Creation

For tests that need an expired token, use `createGuestToken` directly with a past timestamp:

```typescript
import { createGuestToken } from "../../../src/backend/guest/guestToken.js";

function createExpiredGuestToken(guestId: string, gameId: string): string {
  const jwtSecret = process.env.SUPABASE_JWT_SECRET!;
  const pastTimestamp = Date.now() - 60_000; // expired 1 minute ago
  return createGuestToken(guestId, gameId, pastTimestamp, jwtSecret);
}
```

This avoids timer manipulation and directly tests the expiry check in `verifyGuestToken`.

## 6. Helper: Game Play Strategy

Reuse the card-playing strategy from `websocket-game.test.ts`. Rather than extracting to a shared module (which would be a refactor of existing code), duplicate the minimal `pickCardsToPlay` function within `guest-flow.test.ts`. It is ~30 lines and the duplication is acceptable for test code that exercises a specific scenario.

Strategy summary:
- On first play or free play: play lowest single card
- When must beat: play lowest card that beats the last play
- When no card beats: pass (if pass is in validActions)

## 7. Edge Cases

1. **Guest token in body vs header.** The `/guest/claim` endpoint expects the guest token in the request body (`guestToken` field), NOT as the Authorization header. The Authorization header authenticates the registered user making the claim. Tests must verify both paths work correctly.

2. **Session store is in-memory.** Guest sessions are lost on server restart. The `existingGuestId` re-creation flow is the recovery mechanism. Tests verify this works by creating a session, joining, then creating a new session with the same ID.

3. **HMAC secret is the JWT secret.** Guest tokens are signed with `SUPABASE_JWT_SECRET`. Tests run against the same secret (from `supabase status`), so real tokens are verifiable.

4. **Race condition on concurrent joins.** Two guests joining simultaneously could trigger optimistic lock retry in `joinGame`. The test server runs single-threaded (Vitest singleThread mode), so this is not directly testable. The retry logic is already covered by the handler's implementation.

5. **Display name deduplication.** The `createSession` router deduplicates names using existing `playerDisplayNames` on the game. The `joinGame` handler also deduplicates. Tests verify both produce distinct names.

6. **Guest token gameId is not enforced by joinGame.** The auth middleware only checks that the session exists (by guestId). It does not restrict the guest to only the game in their token. A guest with a valid session for game A could theoretically call joinGame for game B. The test documents this as current behavior (not a bug to fix in this LLD).

The test server helper already wires up:
- `GuestSessionStore` (with cleanup loop)
- `createAuthMiddleware(guestSessionStore)` on all authenticated routes
- `createSocketAuthMiddleware(guestSessionStore)` on Socket.IO
- `/guest/session` route (no auth required)
- `/guest/claim` route (registered-only auth)

Everything needed to test the guest flow is already in place.

### Import for token crafting

To create expired/custom tokens for edge case tests:

```typescript
import { createGuestToken } from "../../../src/backend/guest/guestToken.js";
```

This is the same pattern used by the production `createSession.ts` handler.

### Test ordering

Tests within this file are independent (no ordering dependencies). Each `it` block creates its own game and guest sessions. The only shared state is the test server instance (read-only from the tests' perspective — they add data but don't rely on data from other tests).

## 7. E2E Playwright Tests

New file: `e2e/guest-flow.spec.ts`

These tests exercise the guest browser flow end-to-end, using a real browser. They complement the integration tests by verifying the full frontend→backend round trip including cookie management, axios interceptor token attachment, and WebSocket connectivity.

### Test cases

```typescript
// e2e/guest-flow.spec.ts

test.describe("Guest flow", () => {
  test("guest joins via invite link, enters name, and reaches lobby", async ({ browser }) => {
    // Registered user creates a game
    const hostContext = await browser.newContext({ storageState: "e2e/.auth/player1.json" });
    const hostPage = await hostContext.newPage();
    const gameId = await createGame(hostPage, { maxPlayers: 4 });

    // Guest opens the join link (no auth)
    const guestContext = await browser.newContext();
    const guestPage = await guestContext.newPage();
    await guestPage.goto(`/game/${gameId}/join`);

    // Fill in guest name and join
    await guestPage.fill('[data-testid="guest-name-input"]', "GuestAlice");
    await guestPage.click('[data-testid="guest-join-button"]');

    // Should reach the game lobby
    await expect(guestPage.locator('[data-testid="game-lobby"]')).toBeVisible();

    await guestContext.close();
    await hostContext.close();
  });

  test("host sees guest appear in lobby player list", async ({ browser }) => {
    // Host creates game and stays in lobby
    const hostContext = await browser.newContext({ storageState: "e2e/.auth/player1.json" });
    const hostPage = await hostContext.newPage();
    const gameId = await createGame(hostPage, { maxPlayers: 4 });

    // Guest joins
    const guestContext = await browser.newContext();
    const guestPage = await guestContext.newPage();
    await joinAsGuest(guestPage, gameId, "GuestBob");

    // Host should see the guest in the player list
    await expect(hostPage.locator('[data-testid="game-lobby"]')).toContainText("GuestBob");

    await guestContext.close();
    await hostContext.close();
  });

  test("guest can play cards after game starts", async ({ browser }) => {
    // Create a 2-player game: host + guest
    const hostContext = await browser.newContext({ storageState: "e2e/.auth/player1.json" });
    const hostPage = await hostContext.newPage();
    const gameId = await createGame(hostPage, { maxPlayers: 2 });

    // Guest joins
    const guestContext = await browser.newContext();
    const guestPage = await guestContext.newPage();
    await joinAsGuest(guestPage, gameId, "GuestPlayer");

    // Host starts the game
    await hostPage.click('[data-testid="start-game-button"]');

    // Both players should see the game board
    await expect(hostPage.locator('[data-testid="game-board"]')).toBeVisible();
    await expect(guestPage.locator('[data-testid="game-board"]')).toBeVisible();

    await guestContext.close();
    await hostContext.close();
  });

  test("guest navigating directly to /game/:id is redirected to guest entry", async ({ browser }) => {
    // Create a game
    const hostContext = await browser.newContext({ storageState: "e2e/.auth/player1.json" });
    const hostPage = await hostContext.newPage();
    const gameId = await createGame(hostPage, { maxPlayers: 4 });

    // Unauthenticated user goes directly to /game/:id (not /join)
    const guestContext = await browser.newContext();
    const guestPage = await guestContext.newPage();
    await guestPage.goto(`/game/${gameId}`);

    // Should be redirected to guest entry
    await expect(guestPage).toHaveURL(new RegExp(`/game/${gameId}/join`));
    await expect(guestPage.locator('[data-testid="guest-entry"]')).toBeVisible();

    await guestContext.close();
    await hostContext.close();
  });

  test("guest with expired/invalid cookie is shown guest entry again", async ({ browser }) => {
    // Create a game
    const hostContext = await browser.newContext({ storageState: "e2e/.auth/player1.json" });
    const hostPage = await hostContext.newPage();
    const gameId = await createGame(hostPage, { maxPlayers: 4 });

    // Guest with no valid session navigates to game
    const guestContext = await browser.newContext();
    const guestPage = await guestContext.newPage();
    await guestPage.goto(`/game/${gameId}`);

    // Should see guest entry (not an error page)
    await expect(guestPage.locator('[data-testid="guest-entry"]')).toBeVisible();

    await guestContext.close();
    await hostContext.close();
  });
});
```

### Dependencies

- Uses existing helpers from `e2e/helpers/game-helpers.ts` (`createGame`, `joinAsGuest`)
- Uses `storageState` fixtures from `e2e/.auth/player1.json` (created by global-setup)
- Follows the same patterns as `e2e/flows.spec.ts` and `e2e/example.spec.ts`

### What these E2E tests catch that integration tests don't

- Cookie-based guest session persistence across page navigations
- The axios interceptor falling back to guest tokens (the recently fixed bug)
- Vue Router guard behavior for unauthenticated users on `/game/:id`
- WebSocket token attachment from the browser (via `useSocket` composable)
- Real-time lobby updates visible in the host's browser when a guest joins
