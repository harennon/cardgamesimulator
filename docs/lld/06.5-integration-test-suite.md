# LLD 6.5: Integration Test Suite

Backend integration tests that verify cross-layer behavior: auth token verification against real Supabase, REST API flows, and WebSocket game play sequences. This catches the class of bugs that unit tests with mocked dependencies miss (ES256 vs HS256 JWT verification, URL path composition, real database constraints).

---

## 1. Scope

### In scope

- Backend integration test infrastructure using Vitest + supertest + socket.io-client
- Docker Compose test environment (`docker-compose.test.yml`) running backend + Supabase (no frontend)
- Helper utilities for creating Supabase users and obtaining real JWTs
- Helper utilities for establishing authenticated WebSocket connections
- 5-7 critical flow tests:
  1. Auth: Supabase-issued ES256 JWT accepted by backend middleware
  2. Auth: Guest session creation and token verification
  3. REST: Create game returns valid response with auth
  4. REST: Join game (registered user + guest)
  5. WebSocket: Authenticated connection established
  6. WebSocket: Full game play flow (create, join, start, play actions, game over)
  7. WebSocket: Guest plays alongside registered user
- npm script `test:integration` for local execution
- GitHub Actions workflow that boots Docker Compose and runs the suite
- Convention/pattern for future LLDs to add integration tests

### Out of scope

- Browser automation (Playwright/Cypress)
- Frontend component or visual testing
- Performance/load testing
- Testing Supabase auth UI flows (signup form, email confirmation)
- Testing nginx routing (that is frontend container territory)

## 2. Approach

### Key decisions

1. **Vitest as the test runner (same as unit tests).**

   Integration tests use the same `vitest` runner with a separate config file (`vitest.integration.config.ts`). This avoids introducing a new test framework. The separate config sets a longer timeout (30s per test vs the default 5s), different include pattern (`tests/integration/**/*.test.ts`), and `poolOptions.threads.singleThread: true` to avoid parallel test interference on shared database state.

   *Rationale:* One framework, one mental model. Developers run `npm test` for unit tests and `npm run test:integration` for integration tests. No new dependencies for the runner itself.

   **Important:** The existing `vitest.config.ts` uses `include: ["tests/**/*.test.ts"]` which would inadvertently match integration tests during `npm test`. The existing config must add an exclusion: `include: ["tests/**/*.test.ts", "!tests/integration/**"]`. This ensures `npm test` runs only unit tests and `npm run test:integration` (using the separate config) runs only integration tests.

2. **Real Supabase instance (via `supabase start`), not mocks.**

   Integration tests talk to the local Supabase instance (GoTrue for auth, PostgreSQL for storage). This is the entire point: we verify that the backend correctly verifies ES256 JWTs issued by GoTrue, and that TypeORM queries work against real Postgres.

   *Rationale:* The ES256/HS256 bug existed precisely because unit tests mocked JWT verification. Integration tests must use real cryptographic verification against real Supabase-issued tokens.

3. **supertest for HTTP, socket.io-client for WebSocket.**

   supertest wraps the Express app without starting a real HTTP listener (avoids port conflicts). For WebSocket tests, we start the server on an ephemeral port and connect via socket.io-client.

   *Rationale:* supertest is the standard for Express integration testing. socket.io-client is already a project dependency (used by the frontend). Both are lightweight and well-understood.

4. **Test-scoped server lifecycle.**

   Each test file boots its own server instance (on port 0 for OS-assigned ephemeral port) in `beforeAll` and shuts it down in `afterAll`. Tests within a file share the server but each creates its own game/user state. This provides isolation without the overhead of per-test server restarts.

   *Rationale:* Aligns with testing principle 3 (self-contained tests). The server is stateless between games — each test creates fresh users and games, so no cross-test contamination. Using port 0 avoids port conflicts when running in CI.

5. **Docker Compose test config for CI (backend + Supabase only).**

   A dedicated `docker-compose.test.yml` runs only the backend container and the Supabase stack. No frontend/nginx container. The test runner executes on the host (or in a CI step) and connects to the backend container.

   *Alternative for local dev:* Developers run `supabase start` and `npm run test:integration` directly (no Docker for the backend). The Docker Compose approach is primarily for CI reproducibility. Both paths are documented.

6. **Shared test helpers in `tests/integration/helpers/`.**

   Helper functions for user creation, JWT retrieval, and WebSocket connection are extracted into reusable utilities. Future LLDs add their tests under `tests/integration/` and import these helpers.

   *Convention for future LLDs:* Each LLD that adds integration tests creates a file under `tests/integration/` named after the feature (e.g., `tests/integration/turn-timer.test.ts` for LLD 7). Helpers are shared; test files are feature-specific.

### Server bootstrap (testable variant)

The existing `Server` class in `src/backend/server.ts` bundles construction and `listen()` into a class with private members. Integration tests need access to the Express `app` (for supertest) and the HTTP server (for socket.io-client URL). Rather than refactoring the production Server class, the test helper constructs the server using the same components but exposes what tests need.

```typescript
// tests/integration/helpers/testServer.ts (implementation sketch)

export async function createTestServer(): Promise<TestServerContext> {
  // 1. Create Express app with all middleware and routes (same as Server constructor)
  // 2. Create HTTP server on port 0
  // 3. Attach Socket.IO
  // 4. Initialize TypeORM connection against local Supabase Postgres
  //    (DB_HOST/DB_PORT env vars — same real database as production, no mocks, no separate DB)
  // 5. Return { app, httpServer, io, baseUrl, close }
}
```

This duplicates some wiring from `Server` but is acceptable because:
- It is test-only code (not production surface area)
- It avoids modifying the production class to export internals
- It is a single ~40-line function that mirrors the constructor

## 5. Test Specifications

### Test 1: `auth.test.ts` — JWT verification

```
describe("Auth integration")
  it("accepts a Supabase-issued ES256 JWT on REST endpoint")
    - Create user via Supabase SDK (gets real ES256 JWT)
    - POST /createGame with Bearer token
    - Assert 200 response

  it("rejects an expired or invalid JWT")
    - Craft a manually-signed HS256 token (wrong algorithm)
    - POST /createGame with Bearer token
    - Assert 401 response

  it("accepts a valid guest token on REST endpoint")
    - Create a game (as registered user)
    - POST /guest/session with gameId and displayName
    - POST /joinGame with guest token
    - Assert 200 response

  it("rejects a guest token for a non-existent session")
    - Craft a guest token with valid HMAC but non-existent guestId
    - POST /joinGame with Bearer token
    - Assert 401 response
```

### Test 2: `game-crud.test.ts` — Game CRUD

```
describe("Game CRUD integration")
  it("creates a game and returns gameId + gameType")
    - Create user, get JWT
    - POST /createGame { gameType: "big2", maxPlayers: 4 }
    - Assert response has { gameId: uuid, gameType: "big2" }

  it("registered user joins a game")
    - User A creates game
    - User B joins game via POST /joinGame { gameId }
    - Assert 200 response

  it("guest joins a game")
    - User A creates game
    - Create guest session for the game
    - POST /joinGame with guest token
    - Assert 200 response

  it("rejects createGame from guest token")
    - Create guest session
    - POST /createGame with guest token
    - Assert 403 response (AccessDenied)

  it("returns game state via GET /getGameState")
    - Create game, join 2 players
    - GET /getGameState?gameId=...
    - Assert response contains playerIds, status: "CREATED"
```

### Test 3: `websocket-game.test.ts` — Full game via WebSocket

```
describe("WebSocket game flow")
  it("establishes authenticated WebSocket connection")
    - Create user, get JWT
    - Connect socket.io-client with auth.token = JWT
    - Assert connection succeeds (no error event)

  it("rejects WebSocket connection with invalid token")
    - Connect with auth.token = "garbage"
    - Assert connection fails with UNAUTHORIZED error

  it("plays a complete Big2 game via WebSocket")
    - Create 4 users, get JWTs
    - User 1 creates game via REST
    - Users 2-4 join game via REST
    - All 4 connect WebSocket and emit game:join
    - User 1 emits game:start
    - Assert all 4 receive game:state with their hands
    - Play actions in turn order using validActions from state
    - Continue until game completes (status === "COMPLETED")
    - Assert final state has placements for all players

  it("guest connects via WebSocket and plays")
    - User 1 creates game
    - User 2 joins via REST
    - Guest joins via /guest/session + /joinGame
    - All 3 connect WebSocket (guest uses guest token)
    - Start game, verify guest receives game:state
    - Guest plays a valid action
    - Assert action succeeds (ack.success === true)
```

### Invariant checks within the full game test

The full game test asserts after each action:
- `state.players.length` matches expected player count
- `state.status` is "IN_PROGRESS" or "COMPLETED" (never regresses)
- Current player's `validActions` is non-empty while game is in progress
- The acting player's hand size decreases by the number of cards played

## 8. Edge Cases

1. **Supabase not running.** Tests fail fast with a clear error: "Cannot connect to Supabase at localhost:54321. Run `supabase start` first." The `createTestServer` helper checks connectivity in `beforeAll` and throws a descriptive error.

2. **Port conflicts.** Using port 0 (OS-assigned) eliminates port conflicts. The test server resolves its actual port after `listen()` completes.

3. **Database state leakage between tests.** Each test creates unique users (random emails) and games (random UUIDs). No shared data. No `TRUNCATE` between tests — uniqueness handles isolation.

4. **Supabase JWKS endpoint timing.** The backend fetches the JWKS key asynchronously at startup. The `createTestServer` helper includes a small delay (or retry) to ensure the JWKS key is cached before tests proceed. Alternatively, the test can call a health-check endpoint that confirms readiness.

5. **CI Supabase startup time.** `supabase start` pulls Docker images on first run (~60s). The `supabase/setup-cli` action caches this. If cold start is too slow, the workflow uses Docker layer caching.

6. **Full game test determinism.** The full game test does NOT use seeded randomness (that is the unit test approach). Instead, it uses `validActions` to make legal moves regardless of card distribution. This means the test passes for any random deal — it exercises the "play any valid action" path, not a specific card sequence.

7. **WebSocket test cleanup.** Every socket created in a test is disconnected in `afterEach` / `afterAll`. Failure to disconnect causes Jest/Vitest to hang (open handles). The `disconnectSocket` helper handles this.

## 11. Implementation Notes

### Server refactoring NOT required

The `createTestServer` helper duplicates ~40 lines of wiring from `Server.constructor()`. This is intentional. The production `Server` class:
- Has private members (correct for production)
- Calls `this.server.listen(port)` in `start()` (we need port 0)
- Reads env vars at module load (we need to control them)

A test-only factory that assembles the same components is simpler than making the production class test-aware. If the server wiring changes, the test helper must be updated — this is acceptable maintenance cost for a ~40-line function.

### supertest usage pattern

```typescript
import request from "supertest";

// REST tests use supertest against the Express app (no network):
const res = await request(ctx.app)
  .post("/createGame")
  .set("Authorization", `Bearer ${user.accessToken}`)
  .send({ gameType: "big2", maxPlayers: 4, gameOptions: {} });

expect(res.status).toBe(200);
expect(res.body.gameId).toBeDefined();
```

### Socket.IO client usage pattern

```typescript
import { io } from "socket.io-client";

// WebSocket tests connect to the real HTTP server:
const socket = io(ctx.baseUrl, {
  auth: { token: user.accessToken },
  transports: ["websocket"],
});

await new Promise<void>((resolve, reject) => {
  socket.on("connect", resolve);
  socket.on("connect_error", reject);
});
```

### Playing a full game programmatically

The full game test uses this strategy:
1. Start game via `game:start` event
2. Each player listens for `game:state` events
3. When it is a player's turn (`state.currentPlayerId === myId`):
   - Read `state.validActions`
   - Pick the first valid action (deterministic: always plays the first legal option)
   - Emit `game:action` with that action
4. Loop until `state.status === "COMPLETED"`
5. Assert placements exist and all players have a finishing position

This strategy converges because Big2 always terminates (players must play or pass, and eventually all cards are played). The "pick first valid action" approach is simple, deterministic given the same game state, and exercises the full action → state → broadcast cycle.
