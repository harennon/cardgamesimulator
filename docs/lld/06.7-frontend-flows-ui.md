# LLD 6.7: Frontend Flows UI

Style the pre-game screens (login, signup, home, create game, join game, app shell) to be cohesive with the in-game UI from LLD 6. These screens are currently functional but unstyled scaffolding. After this LLD, the entire user journey from arrival to game lobby looks and feels like a single application.

---

## 1. Scope

### In scope

- **App shell** (`App.vue`) — dark-themed navigation bar with auth-aware state (display name, logout), consistent layout wrapper
- **Login page** (`LoginView.vue`) — styled form with card-game aesthetic, validation feedback, error states, links to signup and guest entry
- **Signup page** (`SignupView.vue`) — styled registration form with display name field, validation, success redirect
- **Home / Dashboard** (`HomeView.vue`) — hero actions (Create Game, Join Game), user identity display, placeholder for future stats
- **Create Game page** (`CreateGameView.vue`) — game type selection, player count slider, styled create action
- **Join Game page** (`JoinGameView.vue`) — game code input, join button, error states
- **CSS extension** — add flow-screen variables to `game-variables.css` for shared form/button/layout tokens
- **E2E test specs** — Playwright tests for pre-game user flows (login, signup, create, join)

### Out of scope

- Mobile/responsive layout (Phase 5 polish)
- Animations beyond CSS transitions on hover/focus
- The in-game UI (LLD 6 — already implemented)
- Guest entry view redesign (functional and minimally styled — just apply consistent tokens)
- Turn timer or stats display (LLD 7)
- Game history or recent games list (requires backend stats endpoint — LLD 7)

---

## 2. Approach

### Key decisions

1. **Extend `game-variables.css` rather than creating a separate system.**

   The in-game UI uses CSS custom properties for palette, fonts, and spacing. The pre-game screens will import the same variables and add a small set of form/input/button tokens. This ensures visual cohesion without duplication.

   *Rationale:* One source of truth for the visual language. A user transitioning from login to lobby to game board should never feel like they switched applications.

2. **App shell becomes auth-aware with reactive session state.**

   `App.vue` currently shows static navigation links. This LLD adds a reactive `useAuth` pattern: on mount (and on auth state change via Supabase `onAuthStateChange`), the shell updates to show the user's display name and a logout button when authenticated, or login/signup links when not.

   *Rationale:* The CX doc's home wireframe shows "Welcome, Alice" in the header. Auth state must be globally visible for navigation context.

3. **Dark background applied at the `body` level, not per-component.**

   Currently `body { background-color: #e2e2e2 }` in `index.html`. This LLD changes the body background to `var(--bg-dark)` (#0d0d0d) and imports `game-variables.css` globally (in `main.js` or `App.vue`). Individual page components render on this dark canvas without each needing to set their own backgrounds.

   *Rationale:* Eliminates the jarring light-to-dark flash when navigating from pre-game screens into the game UI. Single source of truth for base styling.

4. **Form components use a shared `.form-card` pattern.**

   Login, signup, create game, and join game all share the same visual pattern: a centered card panel on a dark background with a gold-accented heading, form fields, and a primary action button. Rather than a reusable Vue component (which would be premature abstraction for 4 slightly different forms), this is achieved via shared CSS classes.

   *Rationale:* The forms are simple, few in number, and differ enough (fields, validation, links) that a shared component would add unnecessary prop complexity. Shared CSS classes get the visual consistency without the abstraction overhead.

5. **No component extraction for nav bar.**

   The app shell navigation remains inline in `App.vue`. It is small (logo, 2-3 links, user/logout) and does not warrant a separate component file. If it grows in Phase 5 (mobile hamburger menu), extract then.

   *Rationale:* Simplicity first. The nav has no complex state beyond auth status which is already managed in the shell.

6. **`signOut` navigates to login after success.**

   The logout button calls `signOut()` from `authService.ts` then navigates to `/login`. No confirmation dialog — logout is instant and non-destructive (the user can log back in immediately).

7. **GuestEntryView gets token consistency, not a redesign.**

   `GuestEntryView.vue` already has basic styling and uses `game-variables.css`. This LLD only ensures its button/input styles use the shared `.form-card` tokens where applicable. No structural changes.

**Script logic:**

```typescript
import { ref, onMounted } from "vue";
import { useRouter } from "vue-router";
import { getSession, signOut, supabase } from "@/service/authService";

const router = useRouter();
const isAuthenticated = ref(false);
const displayName = ref("");

onMounted(async () => {
  const session = await getSession();
  updateAuthState(session);

  // Listen for auth changes (login/logout from other tabs or sub-pages)
  supabase.auth.onAuthStateChange((_event, session) => {
    updateAuthState(session);
  });
});

function updateAuthState(session: Session | null) {
  isAuthenticated.value = !!session;
  displayName.value = session?.user?.user_metadata?.display_name
    ?? session?.user?.email
    ?? "";
}

async function logout() {
  await signOut();
  router.push("/login");
}
```

```typescript
const showNav = computed(() => !route.path.match(/^\/game\/[^/]+$/));
```

Change:

To:

The hardcoded value duplicates `--bg-dark` intentionally — CSS custom properties are not available until stylesheets load, and the body color must prevent a white flash on initial page load.

### Import `game-variables.css` globally

In `src/frontend/main.js` (or `main.ts`), add:
```typescript
import "./styles/game-variables.css";
import "./styles/flows.css";
```

This makes the CSS custom properties and shared flow classes available globally, so individual components do not need to `@import` them in their `<style>` blocks.

## 6. State Model

### Auth state in App shell

```
Supabase.auth.onAuthStateChange
  │
  ▼
App.vue (reactive refs: isAuthenticated, displayName)
  │
  ├──► Nav: shows user/logout OR login/signup links
  │
  └──► HomeView: shows actions OR auth prompt
```

Auth state is not shared via a global store (no Pinia). Each component that needs session info calls `getSession()` on mount. The App shell additionally listens to `onAuthStateChange` for reactive updates (e.g., when the user logs in from the Login page, the nav bar updates without a page reload because Vue Router performs a client-side navigation and `App.vue` re-evaluates).

### No new composables

This LLD does not introduce new composables. The existing `authService.ts` provides all needed auth operations. The auth-reactive pattern in `App.vue` is simple enough to live inline (3 refs + 1 listener).

## 7. Edge Cases

| # | Case | Handling |
|---|------|----------|
| 1 | Login with invalid credentials | Supabase returns error message. Display inline below form fields. No page reload. Form fields preserved. |
| 2 | Signup with existing email | Supabase returns "User already registered". Display as form error. |
| 3 | Signup with weak password | Supabase requires min 6 chars. `minlength="6"` on input provides browser hint; server enforces. |
| 4 | Create game — network failure | Catch in `createGame()`, show "Network error" in `form-card__error`. |
| 5 | Join game — game not found | Backend returns 404. Show "Game not found." error. |
| 6 | Join game — game full | Backend returns 409. Show "Game is full." error. |
| 7 | Direct URL to /create-game without auth | Router guard redirects to `/login?redirect=/create-game`. After login, user is forwarded back. |
| 8 | Logout while on protected page | `signOut()` navigates to `/login`. If user was on `/create-game`, they are redirected away. |
| 9 | User refreshes home page | `onMounted` re-checks session. If still valid, shows authenticated view. |
| 10 | Auth token expired | Supabase JS SDK auto-refreshes tokens via `refresh_token`. If refresh fails, `getSession()` returns null and nav shows login links. |

## 12. Implementation Notes

1. **Remove the `<p><strong>Current route = </strong>{{ $route.fullPath }}</p>` debug line** from `App.vue`. It is a development artifact.

2. **Remove the "Load Game" route** from `routes.ts` and the corresponding `LoadGameView.vue` component. There is no CX flow for "Load Game" — it is dead functionality. (If this is a concern, flag for the CEO. The CX doc does not reference it.)

3. **Remove the "About" page link** from the nav. It is not part of the CX flow and adds chrome that violates the "minimal chrome" design principle. The route can stay for direct access but should not be in primary navigation.

4. **Remove the Tonk option** from CreateGameView. Only Big2 is implemented. Showing an unplayable option creates user confusion. Re-add when Tonk is implemented.

5. **`select` element styling:** HTML `<select>` elements have limited CSS styling. The implementer should use the native `<select>` with the `form-card__input` class (which handles background, border, text color) and accept browser-native dropdown styling. A custom dropdown component is out of scope.

6. **No `<style scoped>`** on restyled components. The shared classes from `flows.css` are global. Component-specific additions (like `.home__title`) can be scoped if they do not need to be shared.
