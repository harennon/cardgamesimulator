Screenshot Sourcing & Anti-Rot

The screenshot slots above are NOT bitmap PNGs

There is no public/ or image dir today, and committed PNGs rot the instant the board UI changes (LLD 107/108 just reflowed the board). Two options for the LLD to choose between:

  • Option 1 — Live component thumbnails (recommended). Each step renders real <GameCard> / mini-board markup from static fixture data (the mini-cards above are exactly this). No binary assets; illustrations track the real card renderer automatically. Anti-rot is structural — if GameCard changes, the walkthrough changes with it.
  • Option 2 — Committed PNGs under src/frontend/assets/howto/. Simpler authoring, but rots silently. If chosen, the LLD must add a checklist item to DEVELOPMENT.md ("re-shoot howto images when board UI changes") — an explicit, documented anti-rot process, not a silent one.

Either way the content stays declarative & gameType-keyed: WALKTHROUGHS[gameType] = Step[] where each Step = { illustration, caption }. Adding Tonk later is a data entry, not a code change — mirroring how GameView.vue dispatches <TonkBoard> vs <GameBoard>.

Recommendation

Direction A (modal) + inline (?) entrypoint + persistent FAB cluster, with Option 1 (live component thumbnails). Rationale: the modal matches the zero-friction, no-dead-end CX principle (never leaves the create-game flow), reuses the FeedbackWidget overlay pattern already in the codebase, and the FAB cluster directly implements the user’s feedback. Direction B is best if deep-linking / sharing a rules page matters; Direction C is heavier chrome that pays off only with many steps. Please confirm which you want.
