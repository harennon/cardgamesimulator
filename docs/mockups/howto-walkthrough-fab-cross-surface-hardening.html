LLD 113 · Frontend Mockup · Hardening

Persistent Help FAB — cross-surface edge-case hardening

The single bottom-right cluster (a ? help FAB + a bug icon, delivered by #122) lives in the app shell and is present on every surface. This mockup does not introduce a new aesthetic — it demonstrates the placement + behavior changes needed so the cluster never collides with board controls and behaves sensibly across the lobby, live board, and the game-starts-while-open transition.

Two placement directions are shown side-by-side (A and B). Use the toggle in each section to compare. Everything is a static replica of the real components (same tokens, same z-index stack).

1 · The problem: cluster vs. bottom action row

The cluster sits at right:16px; bottom:16px. On the board the play/pass ActionPanel occupies a --mobile-actions-height: 56px bar pinned to the bottom edge. At narrow widths the cluster overlaps the Pass / Play buttons and can sit on top of the player's own hand. This is the primary AC to resolve.

2 · Two solution directions on the live board

Both keep the cluster in the app shell (never unmounts → socket, timers, and board state are untouched). They differ only in how the cluster yields to the bottom action row.

Direction A — Lift above the action bar. On the board only, the shell reads a CSS custom property --board-safe-bottom (set to the action-row height + gap) so the cluster rises to sit above the Play/Pass row instead of on top of it. On mobile the cluster also collapses to a single ? FAB (the bug icon moves into an expand-on-tap) to reclaim horizontal room next to the hand. Zero layout change on non-board surfaces.

4 · Edge case: game starts while walkthrough is open

A player opens the walkthrough from the lobby, then the host presses Start. Because the walkthrough content is static (no live state), the board renders behind the scrim and nothing is trapped. The proposed behavior: the modal stays open (the user chose to read it) but a non-blocking toast announces the transition, and closing returns them straight onto the now-live board. WHY THIS IS SAFE

Socket & state untouched. The FAB and modal live in the app shell, a sibling of GameView. Opening the modal never remounts GameView, so the Socket.IO connection, useGameState, and the turn timer keep running.

Nothing is trapped. The lobby→board transition happens in GameView underneath the scrim. The modal is a pure overlay; the user closes it (× / Esc / scrim tap) and is on the live board exactly where the game now is.

Sensible nudge. A 3s auto-dismissing toast signals the transition without stealing focus or forcing a close — the user decides when to return.

5 · Interaction & behavior summary

Resting placement (home, create-game, lobby, game-over): cluster at right:16px; bottom:16px — unchanged from #122.

Board placement (IN_PROGRESS / SHOW_FINAL_PLAY): cluster lifts by the action-row height so it never overlaps Play/Pass or the hand. Direction A lifts; Direction B docks top-right into the opponent row.

Mobile: collapse to a single ? FAB near the safe corner; bug/feedback reachable inside the walkthrough footer or the existing feedback path, so the hand keeps full width.

Open/close: no navigation, no socket churn; Esc and scrim-tap close; focus returns to the FAB.

Game-starts-while-open: modal persists, non-blocking toast appears, closing lands the user on the live board.
