5 Screenshot sourcing & anti-rot approach

The problem

  • src/frontend has no public/, assets/, or committed images today — this is greenfield.
  • Hand-captured PNGs rot silently: the board UI changes, the screenshots don't, and nobody notices until a player is confused.

Recommended: render "illustrations" from live components, not captured PNGs

  • Each Big2 step points at a small, deterministic scene built from the real card components (e.g. GameCard.vue) with hard-coded props — exactly the CSS-drawn mini-cards you see in the frames above, but using production components instead of mockup markup.
  • Anti-rot by construction: if GameCard or the felt tokens change, the walkthrough visuals change with them — they can't drift out of sync because they are the same components.
  • Zero binary assets, zero image pipeline, zero capture step. Adding a game later is a data entry (its scenes reference that game's card components) — no rendering-code change, satisfying the acceptance criteria.
Option Sync / anti-rot Cost
Component-rendered scenes pick Cannot rot — reuses live GameCard + tokens Author a tiny scene descriptor per step
Committed PNG screenshots Rots silently; needs a manual re-capture discipline Image dir + capture step + review burden
Playwright auto-captured PNGs in CI Stays fresh, but heavy New CI job, storage, flakiness — over-built for this slice

Content model shape (gameType-keyed, declarative)

  • Mirrors GameView.vue's gameState.gameType === 'tonk' ? TonkBoard : GameBoard dispatch: WALKTHROUGHS[gameType] → ordered steps[], each { scene, title, caption }.
  • The shell takes a gameType, looks up the entry, and renders steps. Adding Tonk later (next sub-issue) is one new key — no shell change.
