01

The correlation key fans out to three surfaces

One ID is minted per session (and re-minted per game) in useFeedbackContext.ts. It is written verbatim to Sentry (as a tag/context), the feedback row (in the existing metadata JSONB — no migration), and every backend log line. Because the same string lands everywhere, a report, a crash, and a log can be joined after the fact — the mechanism that makes log-driven triage possible.

Data flow — mint once, stamp everywhere
correlationId = "cx_9f3a2b7e" minted in useFeedbackContext on session start · rebound to gameId on game join

02

errors.mjs — the queryable artifact (the actual deliverable)

Mirrors feedback.mjs exactly: authenticates via .env.admin, emits a JSON array on stdout. This is what lets a workflow ask "what errors happened for this session?" — without it, the errors sit in a dashboard no workflow can read. This CLI is the end-goal of the whole issue.

Terminal — same invocation shape as triage-feedback
node · scripts/errors.mjs
# lookup by correlation id — "what broke for this session?" $ node scripts/errors.mjs --json --correlation-id cx_9f3a2b7e [ { "correlationId": "cx_9f3a2b7e", "gameId": "abc123", "title": "TypeError: cards.filter is not a function", "type": "TypeError", "culprit": "GameBoard.vue in onPlay", "count": 3, "firstSeen": "2026-07-05T18:22:04Z", "lastSeen": "2026-07-05T18:24:41Z", "permalink": "https://sentry.io/…/issues/40912", "breadcrumbs": "socket:connect_error ×4 (throttled), ui.click ×2, navigation" } ] # most-recent window — feeds error-driven issue creation $ node scripts/errors.mjs --json --since 24h # → JSON array of every issue in the last 24h $

CLI surface

  • --json Machine output. Prints a JSON array to stdout; nothing else. Parity with feedback.mjs --json.
  • --since 24h · --recent Time / most-recent filter for periodic pulls.
  • --correlation-id <id> "What errors happened for this session?" — the join key.
  • --game-id <id> "What errors happened in this game?"
  • Auth: Sentry REST token from .env.admin, same pattern as the feedback CLI.
  • Consumed by: a follow-up workflow (feedback validation or error-driven issue creation) — out of scope here.

Quota safety & the one visible code change

Two design details worth eyeballing: the socket-flap throttle (left) that keeps a bad network from burning the 5,000-event/mo budget, and the feedback widget (right) — the only surface a human touches — gaining a single invisible metadata field.

Socket breadcrumb throttle

useSocket.ts · connect_error / disconnect are not auto-captured — we add them, then rate-limit.

raw events
recorded ✓✓
reconnect storm (12 fires) breadcrumb kept deduped / dropped

Repeating same-reason socket events collapse to 1 per window (e.g. 1 per 10s), carrying a count. A flapping client can no longer fire hundreds of events and exhaust the monthly quota — while a genuine outage still surfaces one breadcrumb with the correlation key + gameId.

05

Design decisions to confirm

There is no visual-direction A/B here — the feature is operator tooling with essentially no player-facing UI. What needs a Frontend decision is the shape of the artifact and the few presentation choices below. Reply with your pick (or "all defaults OK").

Decision Recommended default Alternative
Correlation ID format cx_<8-char nanoid> — short, greppable, human-quotable in a bug report. Full UUID v4 — collision-proof but noisy in logs & tags.
Session vs. game scope One key per session, rebound to gameId on join so a game's errors group cleanly. Two separate keys (sessionId + gameId) tagged independently — more fields, more join logic.
errors.mjs output fields correlationId, gameId, title, type, count, first/last seen, permalink, breadcrumb summary Add raw stack frames & full breadcrumb list (heavier JSON).
Socket throttle window 1 breadcrumb / reason / 10s, carrying a count. Fixed cap of N total socket breadcrumbs per session.
Feedback-widget UI No visible change — correlationId is metadata-only. Show a tiny "ref: cx_9f3a2b7e" line so users can quote it in support chats.

Scope reminder: this issue stops at capture + the errors.mjs artifact + the correlation key. The consumption process (feedback validation vs. error-driven issue creation) is a deliberate follow-up decision. Also out of scope: session replay, distributed tracing, any paid Sentry tier.
