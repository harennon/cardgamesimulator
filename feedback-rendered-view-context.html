Feedback — Rendered-View Context Capture

The feedback widget currently records only route.fullPath, which collides when one route renders several screens. We add two metadata fields: gamePhase (lobby / in-progress / game-over) and authState (authenticated / anonymous). The three directions below differ only in how much of this context is shown to the user — the captured data is identical.

Both new fields are derived client-side at submit time. authState reads the live Supabase session vs. guest cookie; gamePhase needs the live in-game phase (CREATED / IN_PROGRESS / SHOW_FINAL_PLAY + COMPLETED), which today lives as local state inside GameView.vue and is not reachable from the global FeedbackWidget. Surfacing it needs a small shared store/composable — flagged for the architect in the LLD.
Option A

Silent capture — no visible change

Ship the metadata fields with zero UI change. The modal looks exactly as it does today; gamePhase and authState are attached invisibly. Lowest risk, smallest diff, fastest to ship. The only optional affordance is a collapsed "what gets sent" disclosure for transparency (shown expanded in the second scene). Triage gets full context; the player sees nothing new.

Option B

Context chip — passive confirmation

A compact, read-only "Reporting from" chip sits above the actions, showing the auto-detected screen as labelled pills. The player sees that the report knows where they are (builds trust: "it captured the game-over screen, good"), but cannot edit it. Pills are colour- and dot-coded by axis — phase (green), auth (blue) — and never rely on colour alone (text labels + dot shape). Scenes below show the two real collisions from the issue.

Option C

Confirmable context — auto-detected, user-correctable

Same auto-detected pills as B, but the player can correct them if detection is wrong (e.g. a stale phase after a fast transition). Submitted metadata records both the detected value and any override (gamePhaseSource: "auto" | "user"). Highest fidelity for triage, but adds UI surface, a code path that can contradict the real state, and a new metadata field. Likely over-engineered for a derived-from-live-state value — included to show the trade-off.

gamePhase

"lobby" | "in-progress" | "game-over" | undefined. Derived from GameView's displayPhase: CREATED→lobby, IN_PROGRESS→in-progress, SHOW_FINAL_PLAY + COMPLETED→game-over. undefined off /game/:gameId.

authState

"authenticated" | "anonymous". Reads the live Supabase session (authed) vs. a guest cookie / no session (anonymous). Distinct from userType (guest vs. registered) — auth state is the rendered variant, not the account class.

Recommendation

Option B (context chip). It satisfies the "distinguishable in metadata" goal, adds light but real value to the player (confirmation of what's attached), and stays low-risk. A is the fallback if any visible chrome is unwanted; C is over-engineered for a live-derived value.
